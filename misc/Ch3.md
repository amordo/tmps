# Глава 3. Разработка и исследование эффективных алгоритмов параллельной обработки данных на платформе Scala Native
## 3.1. Архитектура и программная реализация параллельного парсера
В данном разделе описывается архитектурное решение разработанного программного комплекса для высокопроизводительного анализа больших объемов текстовых данных (логов). 
Приложение спроектировано в соответствии с паттерном **«Мастер-Воркер» (Master-Worker)**:
* **Мастер-поток (Master Thread):** осуществляет блочный ввод-вывод (I/O), считывая входной файл крупными бинарными блоками (по 8 МБ) для минимизации системных вызовов, и динамически нарезает поток данных на чанки.
* **Рабочие потоки (Worker Threads):** используют встроенный пул потоков `ExecutionContext` и высокоуровневые абстракции `Future` для параллельной обработки выделенных им пакетов данных.
Для обеспечения изоляции данных и исключения взаимных блокировок при аллокации памяти в параллельных потоках применено регионо-ориентированное управление памятью на основе конструкции `Zone.acquire` платформы Scala Native.

## 3.3. Анализ влияния способов аллокации памяти на производительность
В рамках исследования были спроектированы и протестированы две архитектурные модели управления памятью в многопоточной нативной среде:
1. **Модель А (Наивный подход с дублированием контекстов):** Построчное чтение данных, конвертация их в управляемые строки `String` (выделение памяти в куче под управлением Garbage Collector) и последующее избыточное копирование на Си-уровень внутри `Zone`.
2. **Модель Б (Оптимизированный бинарный подход — Zero-Allocation Loop):** Чтение данных плоскими массивами байт напрямую в память региона `Zone` и выполнение поиска подстроки `"ERROR"` на Си-уровне с помощью функции `string.strstr`.
### Результаты сравнительного анализа моделей:

| Системная метрика | Модель А (Наивный подход) | Модель Б (Си-логика в `Zone`) | Изменение (Эффект) |
| :--- | :--- | :--- | :--- |
| **Время выполнения (Real Time)** | 30.65 сек | **1.22 сек** | **Ускорение в ~25 раз** 🚀 |
| **Процессорное время (User Time)** | 70.47 сек | **3.01 сек** | Сокращение затрат в 23.4 раза |
| **Выполненные инструкции CPU** | 957.6 млрд | **39.8 млрд** | Снижение оверхеда в 24 раза |
| **Такты процессора (Cycles)** | 182.7 млрд | **9.3 млрд** | Повышение эффективности конвейера |
| **Пиковая память (Maximum RSS)** | ~566 МБ | ~632 МБ | Оправданный рост ради пропускной способности |

*Вывод по разделу:* Модель Б продемонстрировала колоссальное преимущество, так как полностью исключила фазу аллокации миллионов промежуточных объектов строк в управляемой куче, снизив количество инструкций процессора с 957 до 39 миллиардов. Прирост потребления оперативной памяти (RSS) на 11% обусловлен параллельным удержанием тяжелых бинарных чанков в пуле потоков, что является классическим компромиссом (trade-off) в пользу экстремальной пропускной способности (Throughput).
## 3.4. Оценка масштабируемости параллельной системы (Закон Амдала)
Раздел посвящен исследованию эффективности параллелизма при изменении количества вычислительных узлов (потоков) и размеров бинарных чанков. Описывается точка насыщения системы, при которой дальнейшее масштабирование ограничивается пропускной способностью дисковой подсистемы (переход задачи из категории CPU-bound в I/O-bound).
